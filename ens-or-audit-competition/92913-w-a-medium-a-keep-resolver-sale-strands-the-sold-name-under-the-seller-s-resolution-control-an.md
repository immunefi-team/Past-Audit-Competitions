## #92913 \[W\&A-Medium] A keep-resolver sale strands the sold name under the seller's resolution control -- and if the seller burns the resolver role first, no one can ever undo it

**Submitted on Sep 13th 2026 at 07:43:58 UTC by @I\_A\_J for** [**Audit Competition | ENS**](https://immunefi.com/audit-competition/audit-competition-ens)

* **Report ID:** #92913
* **Report Type:** Websites & Apps
* **Report severity:** Medium
* **Target:** <https://github.com/immunefi-team/audit-comp-ens/tree/audit-comp-ready/apps/portal>
* **Impacts:**
  * Hijacking or bricking an ENS name during a Manager flow (registration, v1 to v2 migration, or transfer), such as: - a registration or migration that assigns the name, its ownership, registry, or resolver to an attacker - redirecting the recipient of a name transfer - leaving a name permanently inaccessible after the flow
  * Taking state-modifying authenticated actions (with or without blockchain state interaction) on behalf of other users without any interaction by that user, such as: Changing registration information Notification/settings changes
  * Causing the application to display or pre-fill an incorrect address, name, or transaction detail, so that a user sends funds or submits a transaction to an unintended recipient, such as: - resolving or rendering an ENS name to an attacker-controlled address - showing the wrong recipient or amount on a transaction the user then approves

### Description

The portal's keep-resolver transfer path neither revokes the seller's resolver-plane roles nor detects a pre-sale burn of the resolver role -- two missing guards in one defective flow, with two executed consequence tiers. Tier 1: the seller keeps ROLE\_SET\_ADDR on the sold name and re-points it at an address they control, while the buyer -- who receives a zero resolver-role bitmap -- cannot edit the records and, holding no \*\_ADMIN, cannot revoke the seller either. Tier 2: if the seller additionally burns ROLE\_SET\_RESOLVER and its admin before the sale, the buyer receives a name permanently pinned to the seller's resolver with no recovery by anyone -- not the buyer, not any future owner, not the registrar, not governance -- while the seller keeps live, updatable control of what the name resolves to. The app ships the exact revocation primitive and already reads the exact role that would reveal the pin; the sale path uses neither

One flow, two missing guards - TransferStepKind is exactly `'set-eth-addr' | 'detach-resolver' | 'detach-registry' | 'transfer-token' (features/transfer/utils/buildTransferPlan.ts:16`) -- **no revoke/role step exists**. The keep-resolver plan is \['set-eth-addr','transfer-token']. Dependency cone: every file under features/transfer/ was scanned; not one imports features/resolver/. Revocation is unreachable from the transfer flow. - This is an unused feature, not a missing one: prepareRevokeResolverRolesTransaction and revokeResolverRoles are live in features/resolver/helpers/revokeResolverRoles.ts, wired into the UI at ResolverRolesSidebar.tsx:227,266. **The app ships the exact remediation primitive and the sale path never invokes it** (captured-only: harness 1's check L2 records the app's own prepareRevokeResolverRolesTransaction succeeding on the fork). - The flow already reads the exact role that would reveal tier 2: features/transfer/hooks/useTransferDetachTargets.ts:81,90 computes heldRoles.includes('ROLE\_SET\_RESOLVER') -- but only to decide whether to *render the detach toggle*. A zero-assignee (burned) state produces no warning and no refusal: the toggle simply doesn't render, and a warning attached to a toggle that never renders never fires.

Tier 1 -- the seller keeps writing the buyer's name The two-plane fact: resolver roles live in the resolver's own EnhancedAccessControl, keyed (resource, account); registry roles are keyed (registry, label) on a different contract. apps/portal/src/lib/roles/resolverRoles.ts:25-44 defines ROLE\_SET\_ADDR: 1n << 0n alongside ROLE\_SET\_ADDR\_ADMIN: (1n << 0n) << 128n. **An ERC-1155 safeTransferFrom on the registry cannot, even in principle, clear a role held on the resolver.** The buyer cannot fix it -- only walk away from it. Revoking ROLE\_SET\_ADDR requires ROLE\_SET\_ADDR\_ADMIN; the buyer receives no resolver roles at all. The revoke UI is gated on canManageRoles (ResolverRolesSidebar.tsx:108, canEdit = canManageRoles && !isSelf), which the buyer fails. Their only remedy is Change Resolver -- abandoning the resolver, not reclaiming it-- and the seller still holds the role on the old resolver afterwards (harness A, test D; captured harness 2, B9). The app documents the resulting state: features/records/hooks/useCanEditRecords.ts:38-41 -- *"After a transfer that keeps the resolver, the previous owner typically retains these roles while the new token owner does not."* canEdit then returns hasResolverRole -- so the buyer reads canEdit === false on a name they own while the seller reads true. The disclosure defence fails on its own text. The keep-resolver warning (SendNameForm.tsx:51) reads verbatim: *"This name's other records will keep resolving after the transfer. Until the recipient updates them, it could still be listed as the primary name for an address that no longer controls it." That warns about stale data persisting. It never says the seller retains write authority*. Different hazards; only the weaker one is disclosed. And for one class of name there is no choice and no warning at all: useTransferDetachTargets makes detachResolver visible only when heldRoles.includes('ROLE\_SET\_RESOLVER') -- a migrated/locked name can own the token yet lack that role (its own comment says so). SendNameForm:98 filters visibleOptions on visibility and :180 renders null when none are visible -- and the warnings render from that same list. So for those names: keep-resolver is forced, no toggle appears, and nothing warns either party. Tier 2 -- a pre-sale burn makes the capture permanent, with no recovery by anyone PermissionedRegistry.\_update -> \_transferRoles(getResource(tokenId), from, to) (:494) moves to the buyer only the roles the seller currently holds; setResolver is gated on ROLE\_SET\_RESOLVER (:150-152). So whatever the seller does not hold at transfer time, the buyer never receives. The seller calls revokeRoles(tokenId, ROLE\_SET\_RESOLVER | ROLE\_SET\_RESOLVER\_ADMIN, self) before selling, driving both assignee counts to zero. ROLE\_SET\_RESOLVER\_ADMIN is self-administering (EACBaseRolesLib.withAdminRolesLib -- only a holder can create another), so once its assignee count is zero it can never be re-created, and ROLE\_SET\_RESOLVER can never be re-granted. No recovery path exists -- enumerated, not assumed (harness B, test\_ENUMERATION\_noRegrantPathExists): recovery would require a holder of ROLE\_SET\_RESOLVER (set the resolver directly) or of ROLE\_SET\_RESOLVER\_ADMIN (grant it), at the token resource or at ROOT (root roles apply to every name). After the burn+sale, all four counts are zero -- with the ROOT read validated (getResource(0)==0 and roleCount(0)!=0 prove ROOT is read with live data). The .eth registry has no resolver-setting governance override even at baseline -- names are self-sovereign -- and the registrar cannot re-grant either (test\_CRITICAL asserts its grantRoles reverts and it holds no root admin). The EAC contracts place no last-admin guard on this path: the only revoke-side revert is count underflow on an already-zero role, and the final-admin burn is executed on real deployed state in harness B (test\_CRITICAL, 6/6). The pin is a property of the registration, and the control is live: - Inherited: the buyer cannot even sell out of it -- transferring onward pins the next owner too (test\_POISON: Bob -> Carol, Carol's setResolver reverts, resolver stays R). - Durable funds-redirect: the seller retains ROLE\_SET\_ADDR on their resolver R, re-points the name post-sale (the UniversalResolver follows, since the name is pinned to R), the buyer can neither write the record nor revoke the seller's role, and a +365 day jump changes none of it (test\_DURABLE). The seller keeps rotating the address to catch payments.

A buyer pays for a name whose resolution is controlled by the seller. Tier 1: the seller re-points the sold name at an address they control; anyone resolving the name -- including third parties paying it -- is directed to the seller (executed: a 5 ETH payment lands at the seller's address while the buyer receives nothing); the buyer cannot correct the records (canEdit === false) and cannot revoke the authority (no \*\_ADMIN); their only escape is to abandon the resolver entirely. Tier 2: the capture is permanent -- the buyer can never change the resolver, never edit the records, and never recover, nor can any future owner, the registrar, or governance, for the entire registration term, while the seller keeps updating the address the name resolves to. Permanent hijack (6286) with a live funds-redirect (6285).
